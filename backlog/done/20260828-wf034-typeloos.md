# typ:null joins WF-034 — the unspelled unknown-type sentinel is refused

Goal: the verifier refuses the explicit Onbekend unknown-type sentinel
(WF-034) but silently admits its unspelled twin: a value node whose typ is
plain null. The skip sits in spec/verifier/lib/checks.ml walk_expr
typ_checks (~1823-1830: None -> []) and in the WF-035 numeriek-operand arm
(~1896-1904: the catch-all skips None). A type:null literal then computes
as a bare unitless number in BOTH executors (ref eval.ml:353-357, clingo
translate.ml:1064-1068 — the None arm shares the Numeriek branch) — the
card-4 lens gap. Facts that make the fence safe: ZERO corpus files
(golden/rood/negatief) carry a type:null literal, and v0's resolver never
emits raw null (it always spells the Onbekend sentinel), so the fence
diverges from no v0 emission and breaks nothing.

The narrowest closing: fold typ:null into the EXISTING WF-034 refusal —
walk_expr's typ_checks rejects a value node without a static type citing
WF-034, exactly symmetric with the Onbekend arm, with the structurally
typeless legitimate node(s) (Lambda) special-cased by NODE KIND, not by
typ_of_expr result. Check after that change whether the WF-035 None-skip
is subsumed; narrow it in the same move ONLY if a type:null operand can
still reach it (smallest change wins). spec/IR-SPEC.md's WF-034 prose
widens by one sentence (the rule covers both the spelled sentinel and a
missing static type). The v0 SCHEMA stays untouched: Literal.type stays
nullable on the wire (mirror-then-diverge; the verifier is the fence).
Executor-level fences in ref/clingo are deliberately NOT added: the gates
replay only verifier-clean IR — record this rejection with its reason in
the card Result.

One new negatief case corpus/negatief/wf034-typeloos-literal/ (directory
name declares the rule): a schema-valid ir.json carrying a type:null
literal in an arithmetic position, which gate 3 must reject CITING WF-034.

### The change (narrowest)
`spec/verifier/lib/checks.ml`, `walk_expr`'s `typ_checks`, the `None` arm only:
a value node whose static type is `None` (plain null on the wire) is now
refused as WF-034 ("value node without a static type"), symmetric with the
existing Onbekend-sentinel arm. The sole structurally-typeless legitimate node,
`Lambda`, is special-cased by NODE KIND (`match e with Lambda _ -> []`), not by
the `typ_of_expr` None result; its own position discipline is WF-069.
`spec/IR-SPEC.md` WF-034 prose widened by one sentence (the rule covers both
spellings — explicit Onbekend sentinel and plain null — with Lambda the only
structural exception). The v0 schema is untouched: `Literal.type` stays nullable
on the wire (mirror-then-diverge; the verifier is the fence).

### Executor-level fences (ref/clingo) — deliberately NOT added, and why
Both executors share the `None` arm with the Numeriek branch — ref
`eval.ml:356` `literal_value` (`Some (Numeriek _ | Percentage _) | None -> ...
Unitless`) and clingo `translate.ml` `expr_term` (idem) — so a type:null literal
WOULD compute as a bare unitless number. No fence was added there because the
gates replay only verifier-clean IR: gate 3 rejects a type:null literal before it
can reach either executor. The single fence lives in the verifier, exactly as the
card prescribes. This rejection of the executor fences is recorded here per the
card's requirement.

### WF-035 subsumption — no narrowing needed (smallest change)
A type:null operand yields `typ_of_expr = None`, and WF-035's numeriek-operand
arm skips `None`; but the Binair arm always recurses into left/right through
`walk_expr`, where the new `typ_checks` fires WF-034 first. Empirically the MAAL
case yields 0 WF-035 violations — caught purely by WF-034. No `None` operand
slips past silently, so WF-035 is left unchanged.

  emits WF-034 alongside its own WF-038 (verified). Gate 3 stays green: WF-038,

  strictly better coverage, not a regression.
- Fence boundary (recorded for a possible future card): the fence inherits

  the legitimate v0 marker) and neither computes as a bare number (lvalue /
  AttribuutRef resolve via attribute datatype, not via node `typ`). Out of this
  card's scope.
